# ego QA

ego-browser 로 로컬 화면을 직접 조작하고, 콘솔 오류·실패한 요청까지 모아 통과/실패를 보고한다.

## 0. 시작 전에

1. `ego-browser skill` 을 실행해 출력(사용 설명서)을 따른다. ego 사용법의 원본은 그 출력이다. 이 스킬은 QA 순서만 담는다.
2. 명령을 못 찾으면 ego lite 설치 여부를 확인한다. 설치 직후라면 새 터미널에서 다시 시도한다(PATH 는 새로 연 프로세스에만 적용된다).
3. Bash 계열은 `ego-browser nodejs <<'EOF' … EOF`, PowerShell 은 `.mjs` 파일 방식으로 실행한다(설명서 참고).
4. **프로젝트 값 찾기**: 앱 주소·포트, 시험 계정, 서버 띄우는 방법, 금지 사항을 다음 순서로 찾는다.
   프로젝트 전용 QA 스킬 → 프로젝트 `AGENTS.md`·`CLAUDE.md` → 개발 서버 실행 스크립트·`package.json`. 계정을 못 찾으면 사용자에게 묻는다.
5. **새 세션에서 시작하길 권한다.** 대화가 이미 길면 호출할 때마다 그 대화 전체를 다시 읽어 토큰이 몇 배로 든다. 긴 작업 세션에서 QA 를 부탁받으면 「다음부터는 새 세션에서 하면 훨씬 싸다」고 한 줄 알리고 **기다리지 않고 지금 세션에서 진행한다.** 사용자가 새 세션으로 옮기겠다고 하면 그때 넘길 요약(무엇을 바꿨나·위험한 곳)을 적어 주고 멈춘다.

## 1. 시나리오 짜기 — 이슈 문구만이 아니라 QA 전문가처럼

이슈·PR 에 적힌 것만 확인하면 QA 가 아니다. **실제 사용자가 할 법한 여러 경우를 직접 만들어 본다.** 시작 전에 시나리오 목록을 적고, 보고 때 무엇을 봤는지 다 보여 준다.

### 1-1. 결과가 퍼지는 곳까지 따라간다

동작 하나의 결과는 그 화면에서 끝나지 않는다. 동작마다 「이 결과가 또 어디에 보여야 하나」를 적고 **그 화면에 직접 가서** 확인한다.

- 다른 앱·다른 역할의 화면: 관리자가 바꾼 것 → 일반 사용자 화면, 사용자가 한 것 → 관리자 목록·상세
- 같은 앱의 다른 화면: 목록 ↔ 상세, 대시보드 숫자·합계, 검색·필터 결과, 내보내기 파일
- 알림·메일·기록: 알림 목록, 보낸 메일(받을 수 있는 시험 주소가 있을 때), 감사·활동 기록
- 되돌리기: 취소·삭제·되돌리면 위의 곳에서도 사라지거나 원래대로 돌아오는지

이슈에 「~하면 사용자 화면에 ~가 나와야 한다」가 있으면 그 화면 확인은 **반드시** 넣는다. 받는 쪽 앱에 로그인할 계정이 없으면 사용자에게 묻고, 끝내 못 보면 「확인 못 함」으로 적는다(통과로 적지 않는다).

### 1-2. 경우의 수 체크리스트

이슈마다 아래에서 **그 기능에 해당하는 것을 골라** 시나리오로 만든다. 다 할 필요는 없지만, 고르지 않은 항목은 왜 뺐는지 한 줄로 남긴다.

| 묶음 | 해 볼 것 |
|---|---|
| 기본 흐름 | 이슈가 말한 정상 동작을 처음부터 끝까지 |
| 입력값 | 빈 값, 최소·최대, 경계값(0·1·한도±1), 너무 긴 글, 특수문자·이모지·한글/영문 섞기, 공백만, 잘못된 형식(메일·전화·날짜) |
| 숫자·돈·날짜 | 소수·음수·0, 큰 금액, 반올림, 월말·윤년·자정 근처, 시간대가 다른 날짜 표시 |
| 상태 | 데이터 0개(빈 화면), 1개, 아주 많을 때(페이지 넘김), 이미 삭제·만료·취소된 대상 |
| 사용자 실수 | 버튼 두 번 누르기, 저장 전에 뒤로 가기·새로고침·창 닫기, 중간에 취소, 같은 걸 두 번 등록 |
| 권한 | 권한 없는 역할로 같은 화면·같은 주소 직접 열기, 로그아웃 뒤 주소 직접 열기, 남의 데이터 주소로 바꿔 열기 |
| 동시성 | 탭 두 개에서 같은 대상 수정, 다른 사용자가 바꾼 뒤 내 화면 새로고침 |
| 유지 | 새로고침·다시 로그인 뒤에도 저장값이 그대로인지, 설정을 바꾸면 실제 동작이 바뀌는지(저장만 되고 효과 없는 설정 찾기) |
| 화면 | 좁은 화면(모바일 폭), 언어 전환, 긴 이름이 줄바꿈될 때, 로딩·오류 상태 문구 |
| 네트워크 | 느린 연결·끊김 중 저장(`page.cdp("Network.emulateNetworkConditions", …)`), 서버 오류 때 화면이 멈추지 않고 안내하는지 |

### 1-3. 우선순위와 분량

- 기본 흐름 → 결과가 퍼지는 곳(1-1) → 돈·권한·데이터 손실 위험 → 나머지 순서로 한다.
- 이슈 하나에 시나리오 8~15개 정도. 위험한 기능(결제·권한·삭제)은 더 한다.
- 이슈와 상관없이 지나가다 본 문제도 「관련 없는 발견」으로 따로 적는다.

### 1-4. 버그를 찾으면

재현 순서(번호 목록) · 기대 결과 · 실제 결과 · 심각도(치명/높음/보통/낮음) · 근거(스냅샷 요약·캡처·콘솔·HTTP 상태)를 적는다. 한 번 더 재현해 보고, 재현이 안 되면 「가끔 발생」으로 적는다.

### 1-5. 시험 데이터

- 시험용 데이터는 직접 만들어 쓴다. 이름 앞에 `QA-<PR번호>-` 를 붙여 누가 봐도 시험 데이터인 걸 알게 한다.
- 남이 만든 기존 데이터는 고치거나 지우지 않는다.
- 바꾼 설정은 끝나면 원래 값으로 되돌린다. 만든 데이터는 지울 수 있으면 지운다.

## 2. 기본 QA 순서

1. 1절에 따라 시나리오 목록을 먼저 적는다(어느 화면 → 무엇을 하면 → 어디에 무엇이 보여야 함).
2. 서버가 켜졌는지 먼저 본다: `curl -s -o /dev/null -w "%{http_code}" <주소>`. 꺼져 있으면 사용자에게 알리거나 허락받고 띄운다.
3. 목표 하나에 작업 공간(TaskSpace) 하나. 앱 여러 개를 동시에 볼 때, 여러 이슈가 묶인 PR(5절)일 때, 사용자가 나눠 달라고 할 때만 공간을 더 연다.
4. 로그인 직후 오류 수집을 켠다(3절). 그다음 시나리오를 진행한다.
5. 진행은 2-1 의 규칙대로 한다(빠르고 싸게, 검증은 그대로).
6. 끝나면 `task.finish({ keep: [] })`. 사용자가 결과 화면을 남겨 달라고 했을 때만 `keep` 에 넣는다.

### 2-1. 빠르고 싸게 — 검증은 줄이지 않는다

토큰과 시간은 「호출 횟수 × 한 번에 읽는 양」으로 늘어난다. 시나리오 수는 줄이지 말고 아래로 줄인다.

- **지금 화면으로 계획할 수 있는 동작은 한 스크립트로 묶는다.** 아는 화면에서 칸 채우기→저장→결과 확인 같은 동작은 한 번에 실행하고 마지막에 결과만 출력한다. 각 단계 뒤에 예상한 화면인지 확인하고(`waitForSelector`·`waitForURL`), 아니면 **그 자리에서 멈추고** 지금 화면을 출력한다. 예상 못 한 창이 떴는데 다음 클릭을 계속하면 엉뚱한 결과를 통과로 적게 된다.
  처음 여는 화면이나 동작 뒤에 생기는 메뉴처럼 **다음 대상을 봐야 정할 수 있으면** 거기서 스냅샷을 출력하고 다음 호출에서 이어 간다. 선택자를 추측해서 묶지 않는다. 서로 다른 시나리오는 묶지 않는다.
- **조건으로 기다린다.** `waitForTimeout()` 같은 고정 대기는 쓰지 않는다. 화면이 늦게 뜨면 틀린 결과가 나오고, 빨리 떠도 시간을 버린다. `waitForSelector()`·`waitForURL()`·`waitForFunction()` 에 `timeout` 을 준다. 애니메이션처럼 조건이 정말 없을 때만 짧게(500ms 이하) 쓴다.
- **출력은 필요한 만큼만.** 전체 스냅샷을 매번 찍지 않는다. 확인할 값은 `page.evaluate()` 로 뽑아 한 줄로 출력하고, 화면 구조를 처음 볼 때·예상과 다를 때만 스냅샷을 찍는다. 한 부분만 보면 되면 `page.snapshot({ scope: "subtree", root: "@ref" })`.
- **스크린샷은 필요한 것만, 한 번만 연다.** 연 이미지는 이후 매 호출마다 다시 읽혀 토큰이 쌓인다.
  - 찍는 것: 실패 근거, PR 캡처, 버튼 잘림·겹침·좁은 화면처럼 눈으로만 알 수 있는 시나리오. 「혹시 몰라」 찍지 않는다(화면 확인은 스냅샷).
  - 보고·PR 에 넘길 캡처는 **한 번 열어** 대상과 상태(로딩 중이 아님, 화면 안에 들어옴)가 담겼는지 확인한다. 잘못 찍혔으면 다시 찍는다. 확인한 파일은 다시 열지 않는다.
- **개발 서버는 미리 깨운다.** 개발 모드 서버는 화면을 처음 열 때 그 화면을 만드느라 수십 초 걸린다. 시험 전에 쓸 화면 주소를 `curl -s -o /dev/null <주소>` 로 한 번씩 열어 둔다.
- **소스 코드는 목적이 있을 때만 읽는다.** 화면 구조를 알아내려고 코드를 훑지 않는다(스냅샷이 더 싸다). 다음 경우에는 읽는다: 돈 계산·상태 변경(결제·일시정지·환불 등)처럼 화면만으로 맞는지 알 수 없는 것, 버그가 의심돼 원인을 확인할 때, 이슈 사이에 얽힌 동작을 시나리오로 만들 때.

## 3. 콘솔 오류·실패한 요청 모으기

ego 는 기본으로 콘솔을 숨긴다(사이트가 자동 조종을 알아채지 못하게). **내 로컬 앱 QA 에서만 켠다.** 외부 사이트에서는 켜지 않는다.

켜기 (공간을 연 첫 스크립트에서 한 번):

```js
await page.cdp("egoAutomated.disable");
await page.cdp("Runtime.enable");
await page.cdp("Network.enable");
```

시나리오를 진행한 스크립트 끝에서 요약 (이벤트는 한 번 읽으면 비워진다):

```js
const issues = [];
for (const e of await page.events()) {
  const p = e.params;
  if (e.method === "Runtime.consoleAPICalled" && p.type === "error")
    issues.push(`console.error: ${p.args.map((a) => a.value ?? a.description ?? "").join(" ").slice(0, 300)}`);
  else if (e.method === "Runtime.exceptionThrown")
    issues.push(`exception: ${(p.exceptionDetails.exception?.description ?? p.exceptionDetails.text).slice(0, 300)}`);
  else if (e.method === "Network.responseReceived" && p.response.status >= 400 && !p.response.url.startsWith("chrome://"))
    issues.push(`HTTP ${p.response.status} ${p.response.url}`);
  else if (e.method === "Network.loadingFailed" && !p.canceled)
    issues.push(`network failed: ${p.errorText} (${p.type})`);
}
console.log({ url: await page.url(), issues });
```

- `waitForURL()` 은 문자열·정규식으로 준다. 함수(predicate)는 받지 않는다.
- 응답 본문이 필요하면 `page.cdp("Network.getResponseBody", { requestId })`.

## 4. 남의 PR 을 받아서 실제로 되는지 시험

1. **PR 파악**: `gh pr view <번호> --json title,body,headRefName,headRefOid,files,closingIssuesReferences`. 본문의 테스트 방법·연결 이슈로 시나리오를 만든다. 바뀐 파일로 어느 앱·화면인지 정한다.
2. **위험한 변경 확인**: DB 마이그레이션·공용 데이터 변경이 있으면 공용 개발 DB 에 적용하지 않는다. 사용자에게 알리고, 프로젝트가 정한 시험 DB 방식을 따르거나 그 변경 없이 볼 수 있는 화면만 본다.
3. **워크트리 만들기**: 지금 작업을 건드리지 않게 따로 받는다.
   ```bash
   git fetch origin refs/pull/<번호>/head
   git worktree add --detach ../<레포>-pr<번호> FETCH_HEAD
   git -C ../<레포>-pr<번호> rev-parse HEAD   # 1번의 headRefOid 와 같아야 한다. 다르면 멈추고 다시 받는다
   ```
   브랜치 이름(`headRefName`)으로 받지 않는다. 포크에서 온 PR 은 origin 에 그 브랜치가 없고, 같은 이름의 다른 브랜치가 있으면 엉뚱한 코드로 시험하게 된다.
   git 에 없는 로컬 설정 파일(`.env*` 등)이 필요하면 원래 폴더에서 복사한다. 의존성을 설치한다.
4. **서버 띄우기**: 이미 켜진 내 서버와 포트가 겹치지 않게 한다. 실행 스크립트가 PID·상태 파일을 공용 위치에 쓰면 그 위치도 나눈다(안 나누면 내 서버 기록을 덮는다).
   **localhost 쿠키는 포트를 가리지 않는다.** 같은 앱을 포트만 바꿔 두 벌 띄우면 로그인 쿠키가 서로 덮인다. 그래서 PR 여러 개를 같은 ego 프로필로 동시에 시험하지 않는다(꼭 해야 하면 ego 프로필을 나눈다 — `help("profiles")`).
5. **시험**: 1~3절 순서로 진행한다. PR 이 고쳤다는 것만이 아니라 1절의 결과가 퍼지는 곳과 경우의 수까지 본다.
6. **증거**: 실패한 단계와 핵심 결과만 스크린샷을 찍는다. 절대 경로로 저장한다(Windows 도 `/` 를 쓴다).
7. **보고**: 사용자에게 아래 표로 알린다. **PR 에 코멘트를 다는 건 사용자가 허락했을 때만** 한다.

   | 묶음 | 시나리오 | 결과 | 근거 |
   |---|---|---|---|
   | 기본 흐름 | ① 관리자 로그인 → 목록 → 수정 저장 | 통과 | 스냅샷 요약 |
   | 퍼지는 곳 | ② 수정한 값이 사용자 화면에 보임 | 실패 | 사용자 화면에 옛 값, 캡처 |
   | 입력값 | ③ 이름 200자 입력 | 확인 못 함 | 사유 |

   결과는 통과 / 실패 / 확인 못 함 셋 중 하나. 실패는 1-4 형식으로 아래에 따로 적는다.
   콘솔 오류·HTTP 4xx/5xx 는 통과한 시나리오에서 나와도 따로 적는다. 1-2 에서 뺀 묶음과 이유도 한 줄로 적는다.
8. **정리**: 띄운 서버 끄기 → `task.finish({ keep: [] })` → `git worktree remove ../<레포>-pr<번호>`. 다시 볼 계획이면 사용자에게 묻고 남긴다.

## 5. 여러 이슈가 묶인 PR (에픽) — 이슈별 병렬 QA

에픽 PR 처럼 하위 이슈가 여러 개면, **서버는 한 벌만 띄우고 이슈마다 작업 공간을 하나씩 열어 동시에** 시험한다.
이 경우는 사용자가 따로 말하지 않아도 공간을 여러 개 연다.

1. **이슈 목록**: PR 본문의 이슈별 절, `closingIssuesReferences`, 에픽의 하위 이슈(`gh api repos/<owner>/<repo>/issues/<에픽번호>/sub_issues --jq '.[] | {number,title,state}'`)로 모은다. 이슈마다 1절대로 시나리오를 만든다. 한 이슈의 결과가 다른 이슈 화면에 퍼지는 것(이슈 사이 연결)도 시나리오로 넣는다.
2. **서버 한 벌**: 4절 3~4번대로 워크트리·서버를 **한 번만** 준비한다. 로그인도 앱마다 한 번 해 둔다(공간끼리 브라우저 로그인을 같이 쓴다). 쓸 화면 주소를 미리 한 번씩 열어 둔다(2-1).
   **안내서를 한 번 만든다**: 본 세션이 이슈마다 화면 주소·누를 버튼 이름·계정·시나리오 목록, 그리고 돈·상태 변경 이슈면 관련 코드 파일 경로를 한 파일에 적는다. 하위 에이전트는 이 안내서로 시작하고, 화면 구조를 알아내려고 코드를 각자 다시 읽지 않는다.
3. **나누기**: 시나리오를 두 묶음으로 가른다.
   - 동시에 돌려도 되는 것: 조회·화면 확인, 서로 다른 데이터를 만드는 입력.
   - 순서대로 돌릴 것: 로그아웃·계정 전환, 다른 화면에 영향을 주는 설정 변경, 같은 데이터를 고치는 것.
4. **병렬 실행**: 동시에 돌릴 묶음은 이슈 하나당 하위 에이전트 하나(Claude 는 Agent 도구, 백그라운드)에 맡긴다. 각 에이전트는 자기 공간을 `taskSpace("PR<번호> #<이슈> <요약>")` 로 열고, 안내서 경로·1절 체크리스트·2-1 규칙·3절 오류 수집 코드를 프롬프트로 받는다. **한 번에 3~4개까지.** 하위 에이전트를 못 쓰는 환경(Codex 등)에서는 이슈별 스크립트를 백그라운드로 동시에 실행한다.
   - **모델 나누기**(Claude): 화면 확인 위주 이슈는 `model: "sonnet"` 으로 띄운다. 돈(결제·청구·환불)·권한·삭제·이슈 사이 얽힘이 있는 이슈는 모델을 지정하지 않는다(본 세션과 같은 모델). 사용자가 모델을 정해 주면 그대로 따른다.
   - **돌려받는 것**: 에이전트는 6번 표의 행과 실패의 1-4 내용만 돌려준다. 스냅샷·로그 원문은 파일로 남기고 경로만 적는다.
5. **다시 확인**: 본 세션이 Sonnet 에이전트의 「실패」와, 돈·권한 시나리오의 「통과」를 직접 한 번 더 재현해 본다. 재현이 안 되면 결과를 고친다.
   그다음 순차 묶음을 순서대로 돌린다.
6. **보고**: 이슈별로 묶어서 하나의 표로 낸다.

   | 이슈 | 묶음 | 시나리오 | 결과 | 근거 |
   |---|---|---|---|---|
   | #101 결제창 카드만 | 기본 흐름 | ① 결제창 열기 → 카드 칸만 보임 | 통과 | 스냅샷 요약 |

7. **정리**: 모든 공간을 `finish` 한 뒤 서버를 한 번 끄고 워크트리를 지운다.

## 6. PR 용 수정 전·후 캡처

- 화면 코드를 고치기 **전에** 전 화면을 먼저 찍는다. 나중에는 못 찍는다. 기본 브랜치를 띄운 다른 워크트리의 서버로 찍어도 된다.
- 같은 공간·같은 창 크기에서 `page.screenshot({ path, fullPage: false })` 로 찍어 크기를 맞춘다.
- 상태를 보여 주려고 공용 DB 데이터를 바꾸지 않는다. 필요하면 응답만 바꿔서 찍고 PR 에 그렇게 적는다.

## 하지 말 것

- 로그인이 막히면 비밀번호를 추측하거나 계정을 새로 만들지 않는다. `task.handOff()` 로 사용자에게 넘긴다.
- 막힌 공간을 버리고 새 공간을 열지 않는다. 멈추고 사용자에게 묻는다.
- 운영(실서비스) 주소에서 QA 하지 않는다. 확인만 필요하면 먼저 묻는다.
